# 概念 → 画面

抽象知识不要只把术语印在图上。先翻译成能看懂的关系，再画。

生图前为每张图写一个很短的 visual plan（给 Agent 看，不要整段塞进 prompt）。

## 流水线

```text
文章
↓ 核心主张（一句话）
↓ 概念关系（谁作用于谁）
↓ 视觉比喻（实物世界里像什么）
↓ 角色动作（这个人在干什么）
↓ 支撑物件（1–3 个）
↓ 场景 + 构图
↓ 短标签（能不加就不加）
```

例：

- 文章：什么是 RAG？
- 主张：生成答案前，先去外部知识里取相关材料
- 关系：外部知识 → 检索 → 模型 → 答案
- 比喻：从书架取出对的书，交给助手
- 动作：角色把一份文档递给 AI
- 物件：书架 + 文档 + 助手
- 标签：检索（可选）

禁止每次都用同一个比喻。RAG 不必永远是图书管理员。

## 一张图一个主观点

好：RAG → 先取资料 → 再生成

差：一张图同时塞 RAG + API + MCP + Agent + Token

文章概念多，就拆到多张图。

## 角色怎么参与

| 元素 | 负责 |
|---|---|
| 角色 | 人的视角，必须动手/互动 |
| 物件 | 抽象概念的实体化 |
| 环境 | 语境（封面暖色场景 / 正文白底迷你剧场） |
| 动作 | 解释本身 |
| 可见结果 | 证据 |

长文正文：去掉角色，图就不成立。  
封面：可以更像主角出场，但仍要和钩子有关，不要纯贴纸。  
知识卡：角色要和短文字/物件一起演戏。

## 常用构图

**对比**：左右分开，用物件和动作显示差别。不要在图里画一张大表格。

**流程**：3–5 步，从左到右。每步一个动作 + 1–3 个物件。不要公司流程图。

**踩坑**：问题必须一眼看得出（断掉的接头、走错的路、溢出的收件箱）。

**前后**：messy → organized，手动 → 自动，困惑 → 清楚。

## 图内文字

图负责让人看懂关系；文章负责讲清楚。

优先：一个概念名、2–8 字标签、短箭头。

禁止：段落、长定义、文章摘抄、假 Logo、密密麻麻小字。

## 附录：AI 术语灵感（不是固定剧本）

先走上面的流水线。下面只是偶尔可借用的起点，**禁止每篇文章都抄同一套**。

| 概念 | 关系 | 可尝试的比喻 |
|---|---|---|
| Model / LLM | 输入 → 生成 | 会吐字的机器、发光核心、引擎 |
| Token | 文本被切成小块再消耗 | 小积木、会被吃掉的筹码 |
| Context | 对话+文件+指令包在一起 | 背包、上下文盒子、桌上相关文件 |
| Prompt | 人给模型的指令 | 指令卡、信封、对话框 |
| RAG | 外部知识 → 检索 → 模型 → 答案 | 取书/取文档交给助手 |
| Embedding | 文字变成可比较的位置 | 文档变成地图上的点，相近的聚在一起 |
| Vector DB | 嵌入后的归档 | 标好的档案架、语义地图连着仓库 |
| API | 系统 A → 接口 → 系统 B | 桥、门、插头、窗口 |
| Function calling | 模型决定 → 调工具 → 返回结果 | 按按钮、把任务卡交给工具 |
| MCP | 模型 ↔ 标准接头 ↔ 多种工具 | 万能接头、总闸、插排（不要画成 Agent 本人） |
| Agent | 目标 → 规划 → 用工具 → 行动 → 结果 | 自己走完几步的助手；要看出自主，不要只画聊天窗 |
| Skill | 可复用的专项能力 | 技能卡、工具箱、装备槽 |
| Loop | 尝试 → 结果 → 评估 → 再试 | 一圈轨道、同一物件的 v1/v2/v3 |
| Memory | 过去信息 → 存起来 → 下次用 | 档案柜、笔记本、记忆盒 |
| Automation | 触发后重复执行 | 传送带、定时机器人 |

产品 / App：角色在用真实任务里的界面，产品要解决一个看得见的问题。
